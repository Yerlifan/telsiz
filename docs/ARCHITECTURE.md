# Telsiz architecture

[Türkçe](MIMARI.md) | [English](ARCHITECTURE.md)

This document describes the Telsiz server, the client, the encryption design, the voice, screen sharing, camera and Telsiz DJ infrastructure, the games played in voice rooms, voice room limits and server information, the desktop app and the release process. The last section lists plainly what the system protects and what it does not. For installation see [DEPLOYMENT.md](DEPLOYMENT.md), and for the visual design see [DESIGN.md](DESIGN.md).

## Overview

Telsiz has three parts: a single process Node.js server, a web client that runs in the browser without a build step, and an optional desktop app that carries the same client inside itself. The server stores accounts, rooms and encrypted content and distributes events between clients. Encryption and decryption happen only in the client. Audio, screen video, camera video and real time game data flow directly between people, and the server only relays the encrypted messages that set up those connections.

```text
 Browser or desktop app                             Telsiz server (Node.js)
 +----------------------------------+   HTTPS     +-----------------------------+
 | public/js/01..46, crypto.js      |  JSON API   | src/app.js   endpoints      |
 | keys exist only here             |<----------->| src/hub.js   long polling   |
 | encrypt, decrypt, search         | long poll   | src/store.js JSON and JSONL |
 +----------------------------------+             +-----------------------------+
        ^        WebRTC (DTLS-SRTP, game data SCTP over DTLS)
        |   audio, screen, camera and game data, peer to peer
        v
 +----------------------------------+
 | other participants               |
 +----------------------------------+
```

## Server

The server runs on Node.js 20 or newer and uses only the built-in modules of Node.js, so `package.json` has no runtime dependencies. The entry point `server.js` reads and validates environment variables, adds the `telsiz.env` file next to it to the environment when running as a single file, sets up the HTTP server with `createChatServer` from `src/app.js`, and on SIGINT or SIGTERM finishes pending writes and exits.

`src/app.js` defines all API endpoints under `/api/`. Authorization is checked on the server at every endpoint, bodies are read with a size limit, and every field goes through type and length checks. There are rate limits per account and per IP address (sign in, registration, messages, uploads, administration, friend requests, typing notifications, voice signals and DJ writes). Session tokens are sent in the `X-Token` header and only their hashes are kept on disk. Behind a reverse proxy, the client address is read only from headers sent by proxies in the `GUVENILIR_VEKIL` list.

Static files are served only from an allowlist: fixed files, and files in the `js/`, `css/`, `css/skins/` and `fonts/` folders whose names match a strict pattern. Path traversal is not possible. The Content Security Policy of the HTML page allows scripts, styles, fonts and connections only from its own origin, allows frames only from `https://www.youtube-nocookie.com`, and prevents the page from being framed by another site. The `'wasm-unsafe-eval'` keyword in the script source allows only WebAssembly compilation and is there for the RNNoise module of advanced noise suppression, which is downloaded from the app's own origin (see Voice). `eval`, `new Function` and inline scripts are still blocked, and there is no `'unsafe-eval'` or `'unsafe-inline'`. API responses and downloaded files are sent with separate policies that cannot run scripts. There are no CORS headers.

The frequency photo (`/api/server-icon`) is public metadata like the frequency name and is not end-to-end encrypted. It is served without a session for the screens before sign-in and for the band of the desktop app that shows other frequencies: the content type detected from the file signature, `X-Content-Type-Options: nosniff`, the same restrictive policy as downloaded files (`default-src 'none'; sandbox`) and an ETag that is the hash of the content (304 for a matching `If-None-Match`). Only the owner can upload and remove it (`POST /api/server-icon`, the body is the image itself, `POST /api/server-icon/delete`), and the admin rate limit applies. The hash is in the `serverIcon` field of `GET /api/info` and of the metadata, and when it changes the meta version goes up and open clients update the photo live. In the browser only the photo of this origin is loaded (`img-src 'self'`), and the stations of other frequencies keep the first letter.

API error messages are in Turkish or English according to the `Accept-Language` header of the request, and console and log messages according to the `DIL` setting or the system language (`src/i18n.js`). In the single file build (`telsiz.exe` and the Linux binaries) the app files are embedded in the executable and read through `src/static-source.js` with the same allowlist.

### Roles and permissions

An account's base role is owner, admin or member. In addition, the owner keeps up to 20 custom roles in the `roles` list of `state.json`: `{ id, name, color, perms }`. The permission keys are `messages` (deleting other people's messages in text rooms), `ban` (banning and kicking from the frequency), `voice` (voice room moderation), `channels` (managing rooms) and `dj` (managing the queue in Telsiz DJ restricted mode), and the color is one of eight fixed keys. The `roleId` of an account record points to the member's single custom role. The owner and admins have every permission, a custom role only adds permissions. The order of the list is the rank: owner, admins, custom roles in list order, and members without a role. Banning, kicking and voice room moderation only apply to someone ranked lower. Kicking (`POST /api/users/kick { userId }`) does the same as deleting the account: the sessions are closed, the name becomes free, and the messages stay with a deleted author. The kicked person's pending poll gets `401 kicked`, and the owner can never be kicked. Only the owner manages roles (`POST /api/roles/create`, `/api/roles/update`, `/api/roles/delete`, `/api/users/custom-role`), and the responses are sent after the state file is written and synced to disk. Roles and the `roleId` and `voiceMuted` fields of accounts are published in the meta, permissions are checked on the server at every endpoint, and the client only adjusts its interface.

Voice room moderation uses `POST /api/voice/moderate { userId, action }`. `mute` and `unmute` change the account's `voiceMuted` field: the field is persistent, stays when the person joins again, and the server shows the person's microphone as off in the crew. Since audio flows directly between people, the mute is applied by the clients: the person's own client keeps the microphone track off and the other clients do not play that person's audio. `disconnect` removes the person's voice sessions on the server, and the other clients close their connection to the person who dropped from the crew. `camera-off` marks the person's open camera as off on the server and is a one time action that is not stored on the account: the person's client stops the local camera when it sees its own camera off in the meta (the same path used when the owner turns cameras off), the other clients do not show the video of a person whose camera is not on in the crew, and the person can turn it on again. If the person is not in a voice room the response is `409 target_not_in_voice`, and if their camera is not on it is `409 target_camera_off`.

### Content reports

A member reports a message they can read (in a text room or in a direct message conversation they belong to) or a person to the frequency owner and admins: `POST /api/reports { kind, channelId?, messageId?, targetUserId, reason, note? }`. `kind` is `message` or `user`, and `reason` is `spam`, `harassment`, `illegal` or `other`. In a message report the room id must be the message's room and the target must be the message's author, a user report has no message fields. Nobody can report their own message or themselves. `note` is an envelope sealed with the group key (the `1.` format, at most 12000 characters), and the server does not accept plain text. The client puts the note, the message text (the quote) and the ids of the reporter, the target and the message into the envelope, and the note and the quote together are at most 2000 characters. The text of a message in a text room goes into the quote automatically, because everyone in the room can read it anyway. The text of a direct message goes in only if the person ticks the box, so it is shown to the owner and admins on purpose. Records are kept in the `reports` list of `state.json`: `{ id, kind, reporterId, targetUserId, channelId, messageId, dm, reason, note, createdAt, resolvedAt, resolvedBy }`. If the same person already has an open report about the same message or person, no new one is created and the response returns the id of the existing record with `duplicate: true` (`{ ok, id, duplicate }`). A person can have at most 20 open reports at a time, and any more get `409 too_many_open_reports`. At most 10 reports per user per hour are accepted (`429`). The list keeps at most 500 records. When it is full the oldest resolved report is dropped first. If all of them are open, the oldest open report of the person with the most open reports is dropped, but only if the reporter will still have fewer open reports than that person after the new one. If no room can be made, a new report gets `503 reports_full`. This way a few accounts cannot fill the list and block everyone else's reports. The per person limit and the full list check run before the hourly limit, so these refusals do not use it up. Only the owner and admins can use the list (`GET /api/reports`, newest first, with names) and resolving (`POST /api/reports/resolve { id }`). An owner or admin who is reported does not see the report about them in the list, does not count it among open reports and cannot resolve it (for them it returns `404 report_not_found` as if it did not exist). So when the owner is reported only the admins see the report, and if the frequency has no admins nobody sees it until an admin is appointed. The client's report dialog tells the person about this. The private view of the owner and admins carries the number of open reports they can see (`reports`) and the id of the newest report they can see (`reportsLast`). When either changes only the pending polls of those people wake up and an open Reports list is refreshed, and a reported owner or admin is not woken up by the report about them. When the list is opened the note is decrypted with the group key, and if the ids in the envelope do not match the record the note is not shown. The reporter writes the quote and nobody can verify it, so the list shows it as "Message text added by the reporter". If the message in a text room is loaded on the device that opens the list and its current text differs from the quote, this is shown too. If the current group key is not on the device, the note and the quote cannot be sealed and the report is sent with the reason only. The responses to reporting and resolving are sent after the state file is written and forced to disk. Nothing is sent to the reported person.

## Real time communication

Real time communication uses only plain HTTP requests with long polling. The reason is that WebSocket and Server-Sent Events support could not be verified in environments such as game console browsers. The client sends a `GET /api/poll` request. If there is something new, the server answers right away, otherwise it holds the request for about 25 seconds and returns an empty answer when the time runs out. This applies to communication between the client and the server: audio, video and real time game data flow directly between people over WebRTC and do not pass through the server, which only carries the encrypted setup messages of these connections (see [Voice](#voice) and [Games](#games)).

`src/hub.js` keeps the following in memory: presence, a ring of recent events, the meta version (rooms, members, roles), each user's private meta version (friends, requests, blocks, the direct message list, and for the owner and admins the number of open reports they can see and the id of the newest one), typing status, voice rosters and voice signal queues. A poll request carries the versions the client knows (`since`, `mv`, `pmv`, `tv`, `muv`, `sig`), the boot id of the server (`boot`), the automatic idle flag of this page (`idle`) and the page id (`tab`). The server sends only the parts that changed. If the client is too far behind, or the server has restarted, the answer carries a resync flag and the client loads its state again from the start.

Every event has an audience: either all members or only specific users. Direct message events go only to the two members of the conversation and never appear in the poll answer of a user outside the audience. A user with the invisible status appears offline to others. Two people with a block between them do not see each other's typing status.

Automatic idle is per session and is kept only in the hub's memory, and there is no new API endpoint. If the client (`40-bosta.js`) sees no mouse, keyboard, touch, wheel or gamepad input on this device for the chosen time (10 minutes by default), it adds `idle=1` to the poll query, otherwise `idle=0`, and restarts the poll when the value changes. The inputs are listened to at the start of the event path, on `window` in the capture phase, so a listener that stops the event (the game keys in a Hexball match) does not hide the input. The gamepad is also read in the gamepad loop that runs on every frame while a gamepad is connected (`21-band.js` `padPoll`), so short taps count too. A device in a voice room is never counted as idle on that frequency, and the server never counts a session in a voice room as idle either. In the desktop app the system idle time (`powerMonitor.getSystemIdleTime`) is counted too, and background windows decide by it alone and do not know about a voice room in the main window. Since the tabs of the same browser and the installed app window share one session, the query also carries a random id of the page made when it opens (`tab`). The hub keeps the last report of each page apart: a session is idle only while every page that reported within the last `pollTimeoutMs` + `graceMs` (40 seconds by default) is idle, the report of a closed tab is forgotten once that time has passed, and at most 8 pages are tracked per session. This way a tab in use and a forgotten tab do not take turns changing the flag of the session. If all of a person's active sessions are idle and the status they chose is Online, the meta shows `status: 'idle'`, and the person sees "Idle (automatic)" on their own side. A chosen Idle, Do Not Disturb or Invisible status does not change, and the idle changes of an invisible person do not bump the meta version. When the shown status changes (poll, a new active session, a session that drops or closes), the meta version is bumped. Since every change triggers a meta broadcast to everyone, a session going idle is accepted at most once every 5 seconds (`idleGapMs`). An earlier change is ignored and the client reports it again on the next poll, and coming back from idle is applied right away. After a server restart the information comes back with the next poll. The decision is based on the difference of `Date.now()` values, not on the timer itself. Chrome can slow the timers of a background tab down to once a minute, so the decision may be up to about a minute late. The Idle Detection API is not used because it asks for permission and exists only in Chromium.

## Persistence

`src/store.js` keeps all data in plain files in the data folder.

| File | Contents and how it is written |
| --- | --- |
| `state.json` | Accounts, session hashes, rooms, roles, the invite code, friendships, blocks, reports, server settings. Written atomically by writing a temporary file and renaming it, and before each write the current valid version is kept as `state.json.bak`. Changes are collected for about 200 ms and reach the disk in a single write. For security relevant actions (password change and reset, sign out and session revocation, account deletion and kicking from the frequency, personal blocks and server bans, role changes, invite code renewal, changing the active group key, sending and resolving reports) the success response is sent only after the file has been written and forced to disk (fsync), and requests waiting at the same time share one write. If the write fails, the request gets a 500 error, the change stays in memory and is written later by the retry loop. |
| `messages/<id>.jsonl` | One encrypted message record per line for each room and direct message conversation. The last 20000 messages per room are kept. The total number of messages across all conversations is limited by `MAKS_TOPLAM_MESAJ` (500000 by default). When it is exceeded, the oldest messages of the conversations with the most messages are removed and a delete record is added to the log. A message line is queued for writing right away, the response does not wait for the write, and lines are not forced to disk with fsync. |
| `server-icon/<hash>.bin` | The frequency photo (PNG, JPEG or WebP, not encrypted). The file name is the first 32 hex digits of the sha256 hash of the content. A new photo is first written to a temporary file, forced to disk and renamed, then its record (`serverIcon`) goes into `state.json` and the response is sent once that record is on disk, and the old file is deleted after that. At startup the file is read and its type and hash are checked, if they do not match the record is removed, and files that are not recorded are cleaned up. |
| `uploads/<id>.bin` | Encrypted files, profile pictures and cover photos. The total size is limited by `YUKLEME_KOTASI_MB` and the size per user by `KULLANICI_YUKLEME_KOTASI_MB`, and uploads not attached to a message are removed after one hour. |
| `.kilit` | The lock of the running process. It prevents a second process from opening the same data folder. |

If `state.json` is corrupt, the server tries to recover from `state.json.bak`. If it can, it first keeps the corrupt file as `state.json.bozuk-<time>` and logs what happened, and if it cannot, it refuses to start. Message bodies are opaque envelopes to the server and are never logged. Telsiz DJ states, presence and automatic idle, typing status and voice rosters exist only in memory and are reset when the server restarts.

## Client

The client is made of plain script files in the `public/` folder. There is no build step, package manager or framework. For compatibility with older WebKit based console browsers the code uses at most ES2017 syntax, and network requests use `XMLHttpRequest`. The page is written only with `createElement` and `textContent`, and no DOM is built from HTML strings.

`index.html` is a single page. First `theme-init.js` applies the theme before the first paint, then the encryption libraries (`vendor/nacl-fast.min.js`, `vendor/scrypt.js`), the dictionaries (`i18n.js`), the encryption helpers (`crypto.js`), emoji data, the Telsiz DJ engine (`music.js`, `dj/youtube.js`), the voice engine (`voice.js`, which also loads `rnnoise-worklet.js` into the audio context for advanced noise suppression) and the numbered modules from `public/js/01-core.js` to `46-hexball.js` are loaded in order. The list of module responsibilities is in [CONTRIBUTING.en.md](../CONTRIBUTING.en.md#project-layout).

The interface uses the Frequency layout: a top bar (the frequency info and the Online strip on the left, Search in the exact center, and the Direct messages, Friends and profile buttons on the right), the frequency band where the joined frequencies (each a separate Telsiz server) are arranged as stations (`24-frekans.js`, pressing a station switches to that frequency), the conversation column in the middle, and on wide screens Notifications with the radio card at the very bottom of the column on the left and the list of text and voice rooms of the open frequency (Stations, with the people in each voice room under it, a sheet opened from the Stations button on narrow screens) on the right. Notifications (`28-bildirim.js`) is a short event list kept only in the client's memory and adds no new data on the server: joining and leaving voice rooms come from comparing the voice rosters (`meta.voice`) with the previous ones on every meta update, while a screen share is written from the encrypted share announcement that arrives over the voice connections, and a game invite from the invite that arrives the same way, so only shares and invites in the same voice room appear. The people in the Stations list are drawn from the same rosters, and the ring around the person speaking is known only in the room you are connected to. In the desktop app hidden background windows count the unread messages of frequencies that are not open (`25-arka-plan.js`, [desktop/README.en.md](../desktop/README.en.md)). Details are in [DESIGN.md](DESIGN.md). The service worker (`sw.js`) caches only the app shell and never touches `/api/` requests.

Moving between conversations lives in `38-gezinme.js`. Room, direct message and Friends switches add an entry to the browser history, and the address and its `#` part never change (that part can carry a key or an invite). An entry carries only the user id, the distance from the root, the view type and a numeric id (`{ telsiz: { v: 1, u, d, view, id } }`). Sheets, the search panel, settings, the image viewer and the profile card add their own entry at every width (`{ telsiz: { v: 1, u, d, overlay } }`), and the entry is taken back when the layer closes some other way. The back button first closes the open layer, then returns to the previous conversation. When a layer without its own entry (a menu, the emoji picker, the enlarged camera view, a confirmation dialog) is on top, back closes only that layer and moves the history back to where it was, so the conversation does not change. Pressing back on the root entry leaves the app through the browser, no trap entry is added. When the session ends (Log Out or a lost session) the history is rewound to the root entry even when no layer is open. The rewind amount is read from the distance stored in the browser's current entry, so it never goes past the root even when the in-memory model is stale. An entry from another account and a history event outside the app are ignored. Read marks (`telsiz.read.<user>`) are kept only on the device and are not synced between devices. A conversation counts as read only while the person is at the bottom and the newest messages are loaded, so a message that arrives while they are scrolled up is not counted as read. The Mark as Read button reads the whole conversation and asks the server for the id of the newest message when the newest messages are not loaded. When a conversation opens and the first unread message is not on the newest page, the page is requested around the last read message (`around`) and newer messages load as the person scrolls down. The unread count comes from both pages together, and it is a lower bound when the pages do not meet. If the conversation was not counted as read when it opened (the person is not at the bottom), this count and the mentions among those messages go into the counters. The startup scan (`scanUnread`, `scanDmUnread`) skips the conversation that opens at startup or after a reload, so this is what keeps its badge when the person moves to another conversation without scrolling down. This needed no server change. The open view (a text room, a direct conversation or Friends, `telsiz.view.<user>`) is stored on the device and restored when the page reloads.

The last eight opened conversations are cached in memory (`38-gezinme.js`, `06-messages.js restoreChannel`). The cache holds the encrypted envelopes from the server, the paging state (whether older and newer messages exist), the first message in the visible area with its offset, whether the person was at the bottom and the pill count. Decrypted text does not go into the cache, and the messages are decrypted and drawn again on return. On return the list is drawn without the skeleton and without asking the server, and the person comes back to where they were (when they left at the bottom, to the New messages divider if new messages arrived, otherwise to the bottom). Then the newest page is requested in the background and merged: missed new messages are added, messages edited since are refreshed, and messages in the range of the newest page that are missing from it were deleted. When the newest page does not meet the loaded messages, newer messages load as the person scrolls down. Events for cached conversations (new, edited and deleted messages) are applied to the cache too. The rule of the open conversation applies: when the person left at the bottom the oldest messages drop once the list goes over 600 messages, and when they left further up the list is not trimmed and the older pages they loaded stay. On a resync (`resync`), when the session starts or ends and when the active group key or the personal identity key changes, the cache is not used. Older messages load on their own when the person gets near the top: when the container of the Load Older Messages button comes within 800 pixels of the visible area (`IntersectionObserver`), or in a browser without the observer when scrolling goes below 400 pixels. They do not load while the person is at the bottom. When a load fails, loading on its own stops for that conversation and the error is reported once, and the button retries. When the startup scan finds the whole newest page (50 messages) unread and older messages exist, the count is a lower bound and the badge shows "50+". The exact count is written once the conversation is opened and its unread messages are counted. Alt with the up and down arrows moves between conversations, Alt+Shift with the up and down arrows moves to the next unread conversation, and Esc counts the conversation as read. These shortcuts do not work when push to talk or another voice key is bound to Alt, Shift or the arrows. These needed no server change either.

Data stored on the device lives in the browser's local storage: the session token, the group keyring (`telsiz.keys`), the personal identity key, pinned contact keys, theme and voice settings, the automatic idle setting, the YouTube consent, read marks and the last open view. The search index exists only in the memory of the session and is never written to disk.

## Encryption

The only cryptographic primitives come from TweetNaCl-js 1.0.3: `secretbox` (XSalsa20-Poly1305) for symmetric encryption, `box` (a shared key over X25519 and XSalsa20-Poly1305) for direct messages, SHA-512 for hashing, and the secure random number generator of the browser. Key derivation from passwords uses scrypt-js 3.0.1. Both libraries sit unmodified under `public/vendor/`, and the checker verifies their sha256 values.

### Group key and envelopes

The group key is a 16 byte random secret. Users see it as a 28 character key code: 26 data characters in Crockford base32 and two checksum characters, in seven groups of four. When a code is typed, case, hyphens and spaces do not matter, and the checksum catches most typing errors. Two values are derived from the secret with domain separated SHA-512: an 8 byte key id (`kid`) and a 32 byte encryption key.

Text room messages, profiles, identity bindings, voice signals and the Telsiz DJ state use the same envelope format: `1.<kid>.<nonce>.<ciphertext>`. The nonce is 24 random bytes for every envelope. The plaintext carries fields that bind the content to its context, for example the author id and the room id in a message. The client checks these fields in every envelope it decrypts, so the server cannot move an envelope to another room or another author.

Files and images are each encrypted with their own random key and nonce. The file key, name, type and dimensions travel inside the encrypted plaintext of the message, and the server sees only the size of the encrypted file. Photos other than GIFs are re-encoded with a canvas before upload, which removes metadata including the location.

The profile picture and the cover photo are also uploads encrypted with their own keys. The profile picture is center-cropped to a square and re-encoded at 256x256, the cover is center-cropped to 3:1 and re-encoded as a 1200x400 JPEG. If the cover exceeds the same size limit as the profile picture (`avatarMaxBytes`), the qualities 0.85, 0.7 and 0.55 are tried in turn. The references to both images (`avatar` and `cover`: upload id, file key, nonce, type and dimensions) travel in the profile envelope encrypted with the group key. The server keeps only the upload ids (`avatarUploadId`, `coverUploadId`) in the user record and serves both images to everyone who is signed in. An upload can be linked only to the uploader's own profile and to a single field, cannot be attached to a message and is not removed by the sweep of unlinked uploads. A changed or removed image is deleted, and both are deleted when the account is deleted. A save from an older client that does not send the `coverUploadId` field removes the cover, so the envelope and the server record stay consistent. The client uses a reference from the envelope only if it matches the upload id on the server. Profile pictures are downloaded when the profile arrives, while the cover is downloaded only when it is about to be shown on the profile card or in the Settings preview. At most 20 covers are kept in memory, the cover that has gone unshown the longest is released and downloaded again when it is about to be shown again.

A new group key can be created. The new key becomes the active key and protects the content that follows, while older keys stay in the keyring on the device to read older messages. The active key only moves forward on a device: a key that a newer key replaced on that device is retired (`telsiz.keys.retired`) and the client never encrypts anything with it again. Only a newer key that the device holds in its keyring, and whose code really yields that key id, replaces the previous one. An unknown key id from the server retires nothing, so the server or an admin cannot retire the real key by announcing a made-up key id first. If the server or an admin switches the active key back to such an older key, sending stays off and a warning appears until a new key is created. So a key known to a removed member or an old invite link cannot be brought back for new content. The group key travels in the part of the invite link after the `#` sign, which browsers do not send to the server.

### Password and account

The password is never sent to the server. The client derives a 32 byte master value with `scrypt(password, salt, N=65536, r=8, p=1)` (64 MiB of memory, about 1 second on a desktop) and produces two keys from it with domain separated SHA-512: the authentication key (`authKey`) that is sent to the server, and the wrapping key (`wrapKey`) that never leaves the device. The server treats `authKey` as a password equivalent and stores a scrypt hash of it. For a username that does not exist, the pre-login endpoint (`/api/prelogin`) returns a fake but consistent salt derived from a server secret, so the answer does not reveal whether the user exists. Accounts created by earlier versions use N=16384. After sign in, the client derives a new salt and N=65536 from the same password in the background, rewraps the same private key with the new wrapping key and sends it with `POST /api/me/kdf`. The server checks the old `authKey` and the old salt, allows the upgrade once per account and only to N=65536, and does not end other sessions. Login device tokens are tied to a random epoch that is renewed on every password change or reset (for older records without one, the SHA-256 digest of the hash). The upgrade does not change the epoch, so other devices keep valid tokens, and the old hash is not kept on disk. For a name that does not exist, the N in the pre-login answer is 16384 or 65536, picked per name by a fixed choice that follows the lowest seen share of accounts on the server that are not upgraded yet. The fake salt for the new N comes from a separate HMAC label and the fake salt for the old N is the value earlier versions served (so after an upgrade a fake answer either stays the same or changes salt and N together), and the share only goes down and is saved to disk, so fake answers never move in a direction real accounts do not. So N alone does not reveal whether an account exists. Someone watching pre-login answers can see the moment a real account's salt and N change, that is, its owner's first sign in after the upgrade. This is an accepted limitation.

### Personal keys and direct messages

Every user has an X25519 identity key pair. The private key is stored on the server wrapped with `wrapKey` (the `1w.` format), so it can be unlocked with the password on every device. The unlocked key exists only in memory and in the local storage of that device.

So that a server without the group key cannot replace personal keys, each user publishes their public key with an identity binding sealed with the group key. The client uses a person's key only if that binding opens, the user id is correct and the key matches the one on the server. Keys are pinned on first sight. If a known key changes, a warning appears in the conversation and sending stays off until the user accepts the new key. Two people can verify each other by comparing a 60 digit safety number derived from their ids and public keys.

The direct message envelope has the format `2.<nonce>.<ciphertext>` and is encrypted with a shared key computed from both parties' keys with `box.before`. The server accepts only the `1.` format in text rooms and only the `2.` format in direct message conversations. There are no group direct messages. For voice and video calls in direct messages, see [Direct message calls](#direct-message-calls).

If a password is reset by the owner or the command line, the server deletes the person's public key, wrapped key, identity binding and recovery code. After signing in with the temporary password, the person chooses a new password, and the new key pair is created and wrapped with that new password in the same request. The server refuses to store a key pair while the account still has the temporary password, so whoever reset it, and therefore knows the temporary password, cannot choose or open the person's new key. If they use the temporary password first, the person can no longer sign in with it and notices. The person can no longer read their old direct messages. When a person changes their own password, the same private key is wrapped again with the new password and direct messages stay readable.

### Recovery code

A person who forgets their password resets it themselves with a recovery code they saved earlier, and the identity key is kept. The code is 16 random bytes written in the same 28 character Crockford base32 format as the group key code, only the checksum label differs (`telsiz-recovery-v1/check`). If a group key code is typed into the recovery field, the client recognizes it and shows a separate warning. Because the secret has 128 bits, the client does not use scrypt and derives two keys with domain separated SHA-512:

- `authKey = hex(first 32 bytes of SHA-512("telsiz-recovery-v1/auth" ‖ secret))` goes to the server, which stores its scrypt hash just like for the password.
- `wrapKey = first 32 bytes of SHA-512("telsiz-recovery-v1/wrap" ‖ secret)` never leaves the device and wraps the identity key a second time in the same `1w.` format as the password.

The `recovery` field of the user record is `{ v: 1, hash, wrappedKey, createdAt, label }` (`label` is the session label of the device that created the code), or `null` when there is no code. A person sees only the creation time and device in their own `/api/state` response, the hash and the wrapped key are never returned.

- Registration and setup create the code together with the account. The code card is shown once (Copy, Download as File), Continue is enabled after the "I saved the code" confirmation.
- The code dialog inside the app does not close without this confirmation: it has no close button, and Escape, the gamepad back button and clicking outside are ignored (locked layer). As soon as the server stores a new code, the device writes a per person "not confirmed" flag (`telsiz.recoveryUnsaved`, holding the creation time of the code), which the confirmation removes. If the page is reloaded or closed before the confirmation, the app warns on the next start and offers to create a new code or to confirm that the code was saved, and Settings > My Account highlights the status. The flag is removed when the code is removed on this device or renewed on another device, and there is no warning while the server has no code.
- `POST /api/me/recovery` creates, renews or removes the code (`recovery: null`). The current password is required and wrong attempts count toward the account action counter. So that someone who once learns the password cannot quietly set up a code and take the account back later, the code changes only with the password, and Settings > My Account shows when and on which device it was created.
- The code stays valid when the password changes. The "Also renew the recovery code" box in the password form renews it in the same request (`POST /api/me/password`, `recovery` field).
- Accounts without a code are reminded once per device after signing in with the password.

Recovery takes two requests without a session:

1. `POST /api/recover/keys { name, recoveryAuthKey }` returns the public key and the private key wrapped with the code when the code is right. The client opens the key with the code and checks that it matches the public key, so a fake wrapped key from the server is noticed.
2. `POST /api/recover` sends the key derivation settings and `authKey` of the new password, the same private key wrapped again with the new password and, mandatorily, a new recovery code. The server checks the code again and returns 409 `keys_changed` if the public key changed (the client then asks for the keys once more). The password hash, key derivation settings, wrapped key, login device epoch and recovery code are renewed, all sessions are signed out, the login counters are reset and a new session is opened on this device. The public key, identity binding and profile version stay the same, so the person reads their old direct messages and the people they talk to see no key change warning. The code works only once, a second request with the same code is refused.

If the account does not exist, has no code or the code is wrong, both endpoints give the same 401 `bad_recovery` response with a dummy hash check of the same cost, so the response cannot be used to scan for usernames. A banned account gets 403 only after the right code. The rate limit is the same per address limit as for sign in, and the per account and address and per username counters are separate from the sign in counters (`r:` prefix): recovery attempts do not lock sign in and failed sign ins do not lock recovery. The login device token of a device that signed in before is honored here too. A password reset by the owner or the command line and account deletion also delete the code. A person without a code is pointed to the owner in the "I don't have a recovery code" section of the sign in screen and loses their old direct messages with the owner's reset.

## Voice

Audio flows over WebRTC as a full mesh: each person in a voice room opens a separate connection to every other person and sends their audio to each one separately. Audio is protected by WebRTC's mandatory encryption (DTLS-SRTP) and does not pass through the server. By default up to 8 people can join a voice room, and the owner can change this limit between 2 and 12 (see Voice room limits and server information).

Connection setup (SDP offers, answers and ICE candidates) is sent with `POST /api/voice/signal` and arrives in the recipient's poll answer. Every signal is encrypted with the group key, and its plaintext carries the peer ids of the sender and the recipient, a connection id and an increasing sequence number. The recipient checks the active key, the sender and recipient pairing and the sequence number, and drops old or repeated signals. A server without the group key therefore cannot change the connection setup or redirect it to someone else. STUN and TURN addresses come from the server when joining a voice room. The same path also carries the messages of the games played in a voice room. For real time game data a data channel can also be opened on top of the voice connection (see [Games](#games)).

Microphone audio passes through a WebAudio pipeline. A detection branch measures the sound without delay, while the audio branch passes the gate with a short look-ahead delay, so syllable onsets are not cut in voice activity mode. In push to talk mode the microphone is open only while the assigned key, mouse side button, gamepad button or on screen button is held. In the desktop app the global push to talk shortcut or the optional key hook uses the same path as a separate source, also while the window is in the background (`desktop/README.en.md`). Speaking is detected on each device from the local audio level. Mute and deafen states are reported to the server so they can be shown to the others.

Advanced noise suppression (RNNoise) suppresses non-speech sounds such as keyboard clicks and hum before they reach others. It is on by default and can be turned off with the switch next to the browser's noise suppression switch in Settings > Voice and video > Voice processing. It turns on and off inside the pipeline without restarting the microphone. The RNNoise node runs in the audio branch, between the source and the look-ahead delay: the AudioWorklet processor in `public/rnnoise-worklet.js` downloads the WebAssembly build of RNNoise (`public/vendor/rnnoise/rnnoise.wasm`) from the app's own origin, compiles it and processes the audio in frames of 480 samples (10 ms) at 48 kHz. If the audio context does not run at 48 kHz, the processor converts the audio to 48 kHz and back internally with linear interpolation. The added delay is about 20 ms. The detection branch keeps measuring the raw sound, so the voice activity threshold, the noise floor and the level meter do not change. The gate, push to talk, mute and mute for everyone are applied after RNNoise. The node does not enter the pipeline before the processor has compiled the wasm file and reported that it is ready. If AudioWorklet or WebAssembly is missing, the files cannot be loaded, the Content Security Policy blocks the compilation or the processor reports an error, the audio continues without a gap with the browser's own processing, no error is shown and the description in the settings states the status.

The browser's noise suppression (`noiseSuppression`) is not turned off while RNNoise is on, and the person's setting applies as it is. The decision is based on a measurement: with a 48 kHz synthetic signal (a vowel sequence, keyboard clicks and pink noise) fed to the fake microphone of Chromium 141, the browser's noise suppression alone reduced the clicks by only about 6 dB. RNNoise reduced the clicks by 26 to 29 dB with the browser's suppression on and by 22 to 33 dB with it off. The speech level dropped by about 1 dB in both cases, and the difference in spectral distortion stayed within the variation between measurements. With both on, the steady noise floor stayed about 5 dB lower. Also, if RNNoise cannot be used, the browser's processing is already running without restarting the microphone. The detailed reasoning is in `public/voice.js`.

The RNNoise files are third party copies and are not modified. The source is the `dist/rnnoise.wasm` file of version 2022.2.0 of the `@shiguredo/rnnoise-wasm` npm package (package license Apache-2.0). According to the package documentation, the license of the wasm file is the BSD-3-Clause license of RNNoise. The build script of the package builds RNNoise from version 2022.1.0 of the `shiguredo/rnnoise` repository. Later versions of this package do not contain a separate wasm file, so this version is used. The same file is included byte for byte in version 0.4.1 of the maintained `@sapphi-red/web-noise-suppressor` package (`dist/rnnoise.wasm`). The JavaScript glue code of Emscripten is not used: the wasm file has only three imports, and their counterparts are in the processor. ## Screen sharing

Screen sharing is built on top of the voice connections. The person sharing picks a screen, window or tab with `getDisplayMedia` and sends an encrypted share announcement to the room. The video track is added only to the connections with people who pressed Watch. The watch request and stopping to watch are also encrypted signals. Adding or removing the video track on a connection uses WebRTC renegotiation.

The person sharing chooses one of four quality levels: 720p at 15 frames per second (the default), 720p at 30, 1080p at 15 and 1080p at 30. The preference for smooth motion or sharp text is passed to the browser as a content hint. The share audio is always requested, and whether it is shared is chosen only in the source picker (the audio option in the browser's picker, or the box in the desktop app's own picker). If the browser provides tab or system audio, it is sent as a track separate from the microphone, otherwise the share continues with video only. The audio is requested with the `restrictOwnAudio` constraint: a browser that supports it and the desktop app remove the sounds Telsiz itself plays (the conversation, notification sounds, Telsiz DJ) from the system audio, so listeners do not hear their own voices back through the share. On older Windows versions that do not support this separation, all system audio is shared. In a full mesh, the upload bandwidth of the person sharing is used separately for each viewer. In the desktop app, the app's own screen and window picker opens instead of the browser picker.

The person sharing can minimize the preview (`22-cast.js`): the stage closes, while sharing and the video sent to viewers continue, and Show Preview appears in the chip in the top bar. The choice is kept on the device in `telsiz.castOwnMin`, and on a narrow screen the preview is always visible because the top bar has no chip there. On the broadcast stage the preview comes last among the modes (watched share, camera grid, game table, preview of your own share): while one of the others is on the stage, Show Preview does not appear, and it appears once that mode closes. The Floating Window button in the stage header opens the room and a Stop button for the person sharing (a preview of their own screen would create a mirror effect), and the watched stream for a viewer, in a floating window (see Floating window). For the person sharing, the preview is minimized only for that share and the saved choice does not change.

## Camera

The camera is also built on top of the voice connections and uses the renegotiation path of screen sharing. The camera is never requested before the person presses the Camera button on the radio card. When they do, the client first asks the server for a slot (`POST /api/voice/camera { on: true }`), and the server checks the owner's setting and the per-room camera limit. If the limit is reached or cameras are turned off, it returns `409 camera_limit` or `403 camera_disabled` and the camera is never opened. Once a slot is granted, `getUserMedia` requests video only (640x360, 15 fps, the front camera with `facingMode: { ideal: 'user' }`, also limited with `applyConstraints` after permission is granted) and the video track is added to every connection in the room. If a camera was selected before, that camera is requested with `deviceId: { exact }` or `facingMode: { exact }`, because Chromium ignores an ideal `deviceId` and opens the default camera. If the camera is missing or busy, the default request is tried, and a permission refusal is not bypassed by the fallback request. The selection is kept in memory for as long as the page stays open. If a camera without a direction (a camera plugged into a computer) was selected, its ID is also kept in browser storage (`telsiz.voice.camera`) and requested even after the page is reloaded, and it is removed when the front or rear camera is selected. Flip Camera (`switchCamera`) goes through the cameras in a cycle: front, rear, then the cameras without a direction in `enumerateDevices` order. A camera's direction is read from `getCapabilities` or from its name. The front and rear cameras are requested with `facingMode: { exact }` and then with the `deviceId: { exact }` of a camera with that direction, and a camera without a direction with `deviceId: { exact }`. The first attempt is the next camera in the cycle, and if the request is refused with `OverconstrainedError` or `NotFoundError`, the rest of the cycle is tried. The new camera is requested while the old one is still open. If the device answers `NotReadableError`, the old camera is released and the request is tried again. If it opens after the release, later switches on that page release the old camera from the start, and if it still does not open (another application is using the target camera) nothing is learned. Phones usually do not refuse the second request but hold it until the old camera is released (Firefox for Android also only opens the permission prompt for the other camera once the old one is released): if the request is not answered within 2.5 seconds, the old camera is released and the same request is still awaited, which leaves the person time to answer a permission prompt. If that request is not answered within 10 seconds either, a second request is sent and whichever arrives first is used, while a stream that arrives late is stopped. If the second request wins, later switches on that page send it 2.5 seconds after the release. If the device is still busy right after the old camera is released (`NotReadableError`), the request is tried once more half a second later. Because a slow camera can also take this path, a timeout does not mark the device as unable to open two cameras. This path is only used for a camera that reports a direction (phones and tablets). For a camera without a direction (computers) and while the browser is asking for permission (`navigator.permissions` camera state `prompt`), the old camera is not released, no second request is sent and the request is awaited for 60 seconds, because on a computer an unanswered request is usually a permission prompt (Firefox asks per camera although the query returns `granted`). If permission is refused after the old camera was released and the old camera cannot be opened again either, the camera turns off with `camera_denied`. After every wait, no new request is sent if the camera has been turned off. The new track replaces the old one on every connection with `replaceTrack`, so no renegotiation and no new server request is needed. If switching fails the old camera keeps running or is opened again by its exact ID, and if that also fails the camera turns off with `camera_lost`. The button only shows when the device has more than one camera (counted again on `devicechange`). Unlike screen sharing, no watch request is needed: while the camera is on it goes to everyone in the room. Sending is limited to about 400 kbps (`setParameters`).

Since transceivers are shared with screen sharing and used in both directions, the m-line that carries the camera is announced to the other side with an encrypted `camera` signal (`{ on, mid }`), and the receiver uses it to tell whether a video track is the camera or the screen. The fact that a camera is on is a field of the voice roster on the server (`meta.voice[room][].camera`), so the server enforces the limit and open clients see it through meta updates. The video itself flows between people encrypted with DTLS-SRTP and does not pass through the Telsiz server. The camera stops when the person presses the button again, leaves the voice room or loses the connection (the server removes the camera state together with the voice membership), the camera device is unplugged or taken by another application (`ended`), or the owner turns cameras off or someone with the voice room moderation permission turns the person's camera off with `camera-off` (in both cases the server treats the camera as off, and the client stops its own camera when meta shows it as off).

## Floating window

The floating window (`public/js/39-yuzen.js`) shows the cameras in a voice room or a direct message call, or profile photos when there are no cameras, in a small always-on-top window. The server does not change, and there is no new API endpoint or signal: the window runs on the same origin and shows names and avatars that are already decrypted, and video streams do not leave the device. A pure function decides what is shown (`floatPlan`): a watched screen share if there is one, otherwise at most 4 camera tiles and a strip of at most 8 avatars for people with their camera off when there are cameras, at most 8 avatars when there are none, and "+N people" for those who don't fit. A ring in the `--live` color lights up around the person speaking. The controls are Microphone, Back to App and Close, and there is deliberately no Leave button.

The script of the app page draws the content: nodes are made in the page and added to the floating document, camera videos are kept with `cameraVideoFor('float-' + person)` and released when the window closes. Because the drawing loop of the app page stops while it is hidden, drawing is scheduled with the floating document's own `requestAnimationFrame` loop. The module connects to the voice state with voice hooks (`voiceHook`) without changing `10-voice.js`: 'change' schedules drawing on every voice snapshot, and 'render' updates the Floating Window button in the tool row of the radio card. The styles are copied from the stylesheets and root attributes (theme, color scheme, font size) of the opening page. The CSP carries over to the floating document too, so no inline styles are used.

The path of the window is chosen by device (`floatMode`):

- The desktop app is checked first, because in Electron 44 document picture-in-picture seems to exist but the window it opens is not visible. The page gets a single-use name from the main process and opens an always-on-top, frameless window without a preload script with `window.open('about:blank', name)` (the only exception to the new window rule, see Desktop app). The window opens by itself when the window is minimized or hidden to the tray (`telsizDesktop.onWindowState`) and closes when the window comes back.
- In the browser, document picture-in-picture (`documentPictureInPicture`, Chrome and Edge 116, desktop Firefox 151) opens with the Floating Window button, within a user gesture. Chrome and Edge also open it when you switch to another tab while in a voice room, through the `enterpictureinpicture` action of `navigator.mediaSession`, and close it when the tab becomes visible. It does not open when the browser is minimized.
- In a browser without document picture-in-picture, the tiles are drawn on a 480x270 canvas at 15 frames per second, and the canvas stream is opened as video picture-in-picture. For a watched stream the stream's own video element is opened, and the `disablePictureInPicture` attribute of the element on the stage is removed right before the request. When the stream is no longer watched (Stop Watching, Expand, the game table, the share ending or its connection being renewed), the stage releases the element's stream, so the window closes instead of staying empty (`22-cast.js` `castSync` calls `floatOnStage` on every render), because switching to the canvas stream is not possible without a user gesture. This window has no buttons, and the microphone is turned on and off from the system media controls (`togglemicrophone`). This path has only been tested in Chromium.

Opening by itself is turned off with the `telsiz.floatAuto` setting on this device (Settings > Voice and Video). Because the floating window appears over other apps, friends' cameras are visible there too. On Windows and macOS the desktop window is excluded from screen capture (`setContentProtection`), while on Linux and in the browser the floating window may appear in a full-screen share.

## Direct message calls

The two members of a direct message conversation can call each other with voice or video while they are friends. Call records are kept in the server's memory per conversation (`src/calls.js`) and are not written to disk, so like voice rooms they are lost when the server restarts. The caller starts the ring with `POST /api/calls/start { dmId, video }` and joins the conversation's channel, the call room. The call appears in the callee's private view (the `call` field, `pmv`) and rings on all of their open devices. The device that accepts joins the call room, and the call becomes active when both members are in the room. The camera turns on only by the person's own choice: Video Call for the caller, and Accept on a video call for the callee. Accept Without Camera, and the Voice Call button pressed while a call from the same person is ringing, join with audio only, so the type the caller chose never turns on the callee's camera. When the incoming call card appears, focus moves to the card itself and not to the accept button, so a key pressed at that moment does not accept the call. Declining and cancelling use `POST /api/calls/decline`. An unanswered call drops after `callRingMs` (45 seconds). A decline only stops the ring on the callee's devices. For the caller the call ends at the end of the ring time, like an unanswered call. So for the caller, a decline cannot be told apart from no answer, not even by timing, and whether the other person is online, invisible or busy does not leak.

Only the two members of the conversation can join the call room, and only while they are friends, have not blocked each other, are not banned or deleted, and a ringing or active call exists in the conversation. For everyone else the conversation does not exist (`404 channel_not_found`). Call information never enters the public meta (`meta.voice`) and does not bump the meta version. It is sent only through the two members' private views, so the other members of the frequency cannot see who is calling whom. Audio and video flow directly between the two people, as in voice rooms, encrypted with DTLS-SRTP.

The call setup signals are encrypted with the two people's personal keys (the `2.` envelope), not with the group key. In the call room the server accepts only the `2.` envelope. The client opens a signal only with the other person's current verified key and never tries old keys. The ciphertext binds the sender and recipient peer ids and the conversation id, and replay protection is the same as in voice rooms. So as long as the other person's key is already pinned on this device, a member who knows the group key cannot get into the call setup even together with the server. If the key is not pinned yet (first contact), the first conversation limit of direct messages applies to calls too: a fake identity binding is pinned on first sight and the call setup stays open to a man in the middle. Only comparing safety numbers reveals it, see [Limits](#limits). Starting and accepting a call require the same key condition as sending a message.

Voice room moderation (mute, disconnect, camera off) and the account-level server mute do not reach private calls. The owner's setting that turns cameras off also applies to private calls, and at most two cameras can be on in a call. Blocking, removing a friend, a ban, a kick from the frequency, deleting the account and the caller's last session ending all end the call. Starting and declining calls are rate limited per user (`callLimit` / `callWindowMs`, 10 per 60 seconds), and a person can have at most one ringing call as the caller at a time.

## Voice room limits and server information

The voice room settings are in the `voice: { capacity, cameras, maxCameras }` field of `state.json` and apply to each voice room separately. The capacity is between 2 and 12, and its default is the `maxVoicePerChannel` option (8). The camera limit is between 1 and 12, its default is 4 and it cannot exceed the capacity. Only the owner can change them with `POST /api/settings { voice }` (admins get `403 forbidden`), the server validates every field (`400 invalid_voice_settings`), the response is sent after the state file is written and flushed to disk, and the meta version increases. The capacity applies when joining, and a lower capacity does not remove the people in the room. When cameras are turned off, open cameras are treated as off.

`GET /api/server-info` (owner and admins only, admin rate limit) returns only numeric facts about the server: processor model and core count, load average (not on Windows), total and free memory, the container memory limit (`/sys/fs/cgroup/memory.max`, otherwise cgroup v1 `memory/memory.limit_in_bytes`, ignoring `max` and unreadable values), free and total space of the disk that holds the data folder (`fs.statfs`, Node.js 18.15 and later, empty otherwise), Node.js version, platform, process uptime, upload and message usage with their limits, the number of people online, in voice and with their camera on, and whether TURN is configured and whether it runs on this machine (`src/system-info.js`).

The recommendation in the settings is calculated in the client with deterministic formulas (`public/js/27-kapasite.js`), and the interface says that it is an estimate. Since voice and video flow in a full mesh, capacity depends mostly on the members' upload speed, not on the server. The input is "the members' typical upload speed" (5 Mbps by default, stored only in the owner's browser). Optionally, the sending rate the browser estimated during the last call on the owner's own device (`availableOutgoingBitrate` from `getStats`) is shown. That measurement also stays on that device, and no measurement is collected from other members. Constants: voice about 40 kbps (`KAPASITE_AUDIO_KBPS`), a 360p 15 fps camera about 400 kbps (`KAPASITE_CAMERA_KBPS`), usable share 70 percent (`KAPASITE_USABLE_SHARE`).

```text
usable = upload (kbps) x 0.7
voice only capacity = largest N with (N - 1) x 40 <= usable = floor(usable / 40) + 1
recommended capacity = largest N with (N - 1) x (40 + 400) <= usable = floor(usable / 440) + 1
recommended camera limit = recommended capacity
```

In a full mesh, someone with their camera on sends their voice and video to everyone else in the room separately, so their upload is the bottleneck. The recommended capacity is calculated from that person's upload, so everyone in the room can turn their camera on. The camera limit assumes that download speed is no lower than upload speed, because in the recommended room each person downloads at most as much video as the person with the camera uploads. The capacity is clamped between 2 and 12 and the camera limit between 1 and the capacity. For example, at 5 Mbps usable is 3500 kbps, the recommended capacity is 8 and the camera limit is 8 (without cameras a voice room can grow to 12 people), and at 50 Mbps both are 12. Server hints are also calculated from the facts: a warning when free disk space is less than the rest of the upload quota or less than 1 GB, when the estimated memory the message cap would take (1500 bytes per message) is more than half of the usable memory (the cgroup limit if there is one), or when the 5 minute load average is more than 1 per core, and an informational hint when TURN runs on this machine or is not configured.

## Telsiz DJ

Telsiz DJ keeps a single music session for each voice room: the current track, the queue, whether it is playing or paused, and an anchor (a server time and a position in the track) used to compute the shared position. The whole state is one envelope encrypted with the group key. The plaintext is bound to the room id and the music context, and it is strictly validated after decryption.

The server (`src/music.js`) keeps this envelope only in memory and cannot see its contents. What the server knows is a version counter, the acceptance time, the size of the envelope and the ids of the users who wrote it. Writes are compare-and-swap: the client sends the version it expects, if that version is not current the write is not applied and the current record is returned, and the client applies its operation again on top of the new state. Only people in that voice room can write. The state of an empty room is removed after 30 minutes.

Each device plays the music in its own player and computes the position from the anchor. A new track, a track change and resuming are anchored ahead by a start lead: 3 seconds for YouTube tracks and 1.5 seconds for audio files. Devices load during this time and start at the same moment from the same position. If the drift exceeds 1.5 seconds, the position is corrected silently. Shared audio files are encrypted uploads like message attachments and are decrypted and played on the device. YouTube tracks play in the official YouTube embedded player inside an isolated frame from the `youtube-nocookie.com` origin. No Google code runs in the app's own origin, and the YouTube API scripts are not loaded. The frame is never loaded before the person gives consent on that device, and the consent can be withdrawn in Settings > Privacy and security.

A single YouTube frame is used for the whole session in the voice room. When the track changes, the frame is not rebuilt: the new video is prepared in the same frame with the IFrame Player API's `cueVideoById` command (the video loads but does not play) and the devices start it at the shared anchor. This way the frame's loading time is not paid again for every track, while the time to fetch the video's information from YouTube is still paid for every track. `loadVideoById` is not used, because the video has to start at the shared anchor on every device, not when the command arrives. The next track is not prepared in advance: the player in the frame holds one video at a time, and preparing the next video would replace the one that is playing. The intent is also to carry the permission to play that the person gave with a tap in the frame over to the following tracks. This behaviour and the order of the messages the frame sends after the command have only been tested with the fake player and have not been tried with the real YouTube yet (on desktop or on a phone). Messages about the old video that are still on their way when the command is sent (position, duration, name, playing or ended state, an error, a blocked playback) are not written to the new track: they are ignored until the frame reports the video cued or unstarted state or the new video's ID, for at most 1.5 seconds. A message that carries the ID of another video does not end this wait. Error and blocked playback reports that arrive meanwhile are held back. If the new video reports itself they belong to the old video and are dropped, otherwise they are applied when the time is up. If the track changes again before the previous video is ready, the frame is not reused and a new frame is built. If the frame's document is reloaded it opens the first video of its address, so the frame is then sent to the address of the playing video. While an audio file plays, the frame waits paused and its events go to no track. The frame is removed when the session ends (no track is left to play), when the consent is withdrawn, when the YouTube source or Telsiz DJ is turned off, when the person leaves the voice room or moves to another voice room, and when the player area changes. If the player reported an error or is not ready yet, the next track opens in a new frame. The frame's origin, its sandbox flags, the origin and source checks on incoming messages and the consent rule do not change.

Audio file tracks play in a single `<audio>` element for the lifetime of the engine, and only the source address changes when the track changes. The interface draws the card right away on the engine's track and state events. While the page is hidden (a background tab, a minimized window) the browser holds back animation frames, so drawing is done with a timer, and the YouTube player area is drawn at least 200x200 in the background too and the track starts together with the other devices. When the card is not visible, the player is moved to one of the four corners and can be minimized. The engine's local hold (a minimized player, a minimized window or a window hidden in the tray reported in the desktop app by `telsizDesktop.onWindowState`, Pause in the system's media controls) only stops the player on that device and does not change the shared state. When the hold is released, the player jumps to the shared position. The hold from Pause in the media controls is also lifted by the `/resume` command and when the person leaves the voice room. The bar of the player in the corner shows a hold the person can release (media controls, minimize), and while it is active the bar's button does not pause the room and only releases the hold. A YouTube track is not played while its player is not visible, and the minimize and window holds apply only to YouTube tracks.

When a track is added, the client of the person adding it sends an encrypted announcement message to the text room. The `d` field in the plaintext of the message is `{ op: 'add', src: 'yt', vid, title }`, `{ op: 'add', src: 'file', title }` for an audio file attached to the same message (`/play` with an attachment), or `{ op: 'add', src: 'fileref', title }` for an audio file in another message added with "Play in DJ". `title` is optional, the receiver removes control and direction characters from it and shortens it to at most 120 code points, and older clients ignore the field. A `fileref` announcement has no attachment. Older clients that do not know this source ignore the `d` field and show the text of the message, so the text of that announcement is the full translated announcement. A Telsiz DJ announcement does not count as an @ mention: the client draws the announcement instead of the text in the message, and the mention counter, notifications and the Mentions Me filter in search do not look at the text of the announcement. The name in the text of a `fileref` announcement is chosen by the person who uploaded the file, and older clients look for mentions in that text, so every @ sign in the name is written as a full width at sign (U+FF20) in the text. The name of a YouTube track may not be known when it is added, and the first device that loads its player writes the name into the DJ state. The person adding waits up to 8 seconds, if no name arrives or the page is hidden or closed in the meantime the announcement goes out without it, and once the name arrives the person adding edits their own message. The server only checks the author of an edit, cannot see the body and does not keep its earlier version. So the edited label is only hidden for an edit the client followed in the open conversation and compared with the earlier version: the earlier version is a DJ announcement without a name that was never edited, the new version only adds the name with the same source and video, and the edit is made within 10 minutes of sending the announcement (with one minute allowed for delay). An edit whose earlier version is not known (the conversation was opened later, the page was reloaded) and every other edit shows the label.

If the server owner turns off Telsiz DJ, the server rejects DJ writes. If the YouTube source is turned off, the restriction is applied on the members' devices, since the server cannot see the encrypted state. When restricted mode (`music.restricted`) is on and someone with the DJ permission is in the room, the server rejects writes from people without the permission with `403 dj_restricted`. If nobody with the DJ permission is in the room, everyone can write, so end of track transitions (the clients' automatic writes) continue after the DJ leaves.

If a device cannot open the music state because it does not have the key, it keeps the record and decrypts the same version again once the key is added (on the key screen, in Settings, or on every poll and meta update).

**Search by song name.** If the argument of the `/play` command does not look like a link (no scheme such as `x://` appears anywhere in it, and none of its words starts with `www.`, is a known YouTube domain or is a domain with a path such as `example.com/x`), the engine treats it as a song name and leaves the search to the interface (`needs_search`). If the owner has turned on search (`music.search`, off by default, true in the meta only while Telsiz DJ and the YouTube source are also on), the interface sends `POST /api/music/search { channelId, q }` and adds the first result with its title through `addYouTube`. The announcement goes out with the title right away. The search is made for the voice room where the command was given: if this device is in another voice room or in no voice room when the response arrives, the track is not added and the person sees an error message saying so. When the room changes, the "searching" line on the card goes away, and the response of the old search does not change the card. If search is off or fails, the interface shows a clear error message and a link to YouTube's results page on the DJ card (in a new tab, `rel="noopener noreferrer"`), and the owner also sees where the setting is. The client sends no request to YouTube, and the Content Security Policy does not change.

The server endpoint runs the same checks as `/api/music/state` (the person is in that voice room, the DJ permission in restricted mode). The query is between 1 and 200 code points, and control characters become spaces. It accepts 10 requests per minute per user and at most 300 YouTube requests in the last 24 hours across the server (`429 rate_limited`, `429 search_daily_limit`). The cap is charged right before each request to YouTube: a search makes at most two requests, and the results page fallback is skipped when no allowance is left for it. A search refused while search is paused after repeated failures (see below) does not count. When the server shuts down, a running search is cut off and the fallback is not tried. The same query (lowercased) is kept in memory for 10 minutes, and identical queries arriving at the same time share one search. The response holds at most 5 results: `{ results: [{ videoId, title, channel, durationS }] }`. The ID must match `^[A-Za-z0-9_-]{11}$`, and the title and channel name are cleaned of control and direction characters and cut to 120 code points. The errors are `503 search_unavailable` (the setting is off) and `502 search_failed` (no usable response from YouTube). The search text is not logged.

The search does not use the official YouTube Data API (`src/youtube-search.js`, no dependencies, `node:https`). The server first calls the search endpoint of YouTube's web interface: `POST https://www.youtube.com/youtubei/v1/search?prettyPrint=false` with the body `{ context: { client: { clientName: 'WEB', clientVersion, hl: 'en', gl: 'US', utcOffsetMinutes: 0 }, user: {} }, query, params: 'EgIQAQ%3D%3D' }` (a video only filter). No `key` is sent, and the `Cookie: SOCS=CAI` header that an open source client sends for the EU consent page is added (its effect could not be verified). If the response cannot be used, the results page (`GET https://www.youtube.com/results?search_query=...&sp=EgIQAQ%3D%3D&hl=en&gl=US`) is read, and its `ytInitialData` object is cut out with a brace counter that knows about strings and escape characters. The client version on that page (`INNERTUBE_CONTEXT_CLIENT_VERSION`) replaces the default in memory (`2.20260720.04.00`). The two requests may take 8 seconds in total, redirects are not followed, compression is not requested, and at most 4 MB of a JSON response and 6 MB of a page are read. The parser walks the tree with an explicit stack (at most 200000 nodes and 64 levels) and collects only `videoRenderer` nodes (and their compact and grid forms) and `lockupViewModel` nodes whose type is `LOCKUP_CONTENT_TYPE_VIDEO`. It does not descend into ads (`adSlotRenderer`, `searchPyvRenderer`, `promoted...` and similar), shelves, channels, playlists or the side column. Items whose duration cannot be parsed as `H:MM:SS`, and items marked as live or upcoming, are skipped, and each ID is taken once. If the structure is not recognized at all (neither a results container nor a known video node), the response counts as unusable. After 3 unusable responses in a row the search turns off for 1 hour, and a single warning line without the search text is written to the server log (`log.musicSearchPaused`, with the reason). Network errors and timeouts are not counted.

The format knowledge was extracted from the source code of open source InnerTube clients (youtubei.js, youtubei, @distube/ytsr, ytsr, youtube-sr) and tested with hand-made sample responses (`test/fixtures/yt-arama/`). Since the development environment cannot reach youtube.com, it has never been tried against the real YouTube, and the first live test has to be done on the server. Things to check in that test: the status code, content type and body size of the request without a key and with the suggested headers, the node names of the result items (`videoRenderer` or `lockupViewModel`, which ad nodes), which encoding of the `params` filter is applied, whether an old `clientVersion` value is rejected, whether a server in the EU is redirected without the consent cookie, whether the results page has the `var ytInitialData = ` marker and the client version, the badge values of live and upcoming streams, and the real response sizes. The 4 MB, 6 MB and 200000 node limits can be narrowed based on the measured sizes, and slices of real responses with IDs and personal data removed can be added to the test data. Tests never reach the real network: the `createChatServer` option `youtubeSearch` can be a function that replaces the searcher, or a fake request function given to the real parser (`{ request }`).

## Games

People in a voice room can play games together. There are two games. Renk is a color and number matching card game for 2 to 8 players with a 108 card deck. Hexball is a real time football game seen from above that 2 to 8 people at the table play in two teams (see [Hexball and the game data channel](#hexball-and-the-game-data-channel)). Games are played only in voice rooms, and there are no games in private calls. Nothing changes on the server: game messages travel on the signal path of the voice room (`POST /api/voice/signal`), and the server cannot tell them apart from other voice signals. The real time data of Hexball, on the other hand, flows directly between people over a data channel on top of the voice connection. The person who sets up the table is the dealer (called Dealer in Renk and Host in Hexball in the interface), plays as well and chooses the rule set: in Renk Official, or Stacking, where a +2 can go on a +2 and a +4 on a +4, and in Hexball one of three field presets. The choice can be changed until Start. If the dealer leaves the voice room, the game ends. In Renk, if a player leaves, their cards go back to the draw pile, the pile is shuffled again and the game continues with the rest, and it ends if fewer than two remain.

A game has four layers. `voice.js` only carries messages: a signal of type `game` carries the fields `{ type, sid, n, p }`, and `p` is a payload of at most 11000 printable ASCII characters whose meaning is hidden from the voice engine. Like screen and camera signals, an invalid game signal is dropped without using up a sequence number, and only a game message from a connection whose first negotiation has finished and from the same connection (`sid`) reaches the game layer. The voice engine reports four events to the game layer: an incoming message (`message`), a connection is ready (`peer-ready`, once per connection), a person left the roster (`peer-leave`) and the voice session ended (`reset`). `33-oyun-protokol.js` (`window.TelsizGame`) holds the message formats, the inner envelope, the counter rules and the randomness helpers, `34-oyun-masa.js` (`window.TelsizGameDesk`) the dealer and player state machines, and `35-renk-kural.js` (`window.TelsizRenk`) the Renk rule engine. These three modules are pure: they use no DOM, clock or network, and time and sending are passed in from outside. This lets the tests run them with real encryption in a four device network simulation with loss, duplicates and page reloads. `36-oyun.js` sets up the environment of this device and draws the general interface, `37-renk.js` draws the Renk table and `46-hexball.js` the Hexball table. A new game is added through the same app contract: the id and limits (`id`, `RULES`, `DEFAULT_RULES`, `MIN_PLAYERS`, `MAX_PLAYERS`), the state functions (`newGame`, `validateMove`, `applyMove`, `removePlayer`, `endGame`, `isOver`, `turnOf`), the views (`publicView`, `privateView`, `legalMoves`) and their validators (`validateView`, `validatePrivate`). The optional `DELAYED_MOVES` list says which of the dealer's own out of turn moves are handled with a 300 ms delay (Last Card and Catch in Renk), and the moves of a game without this list have no delay. The rule engine is added to the `GAME_ENGINES` table in `36-oyun.js`, and the game's interface registers itself with `gameUiRegister`. The optional hooks of the interface contract also make room for a real time game: `onVoiceEvent` receives voice events, `onData` the binary data from the game data channel, `ownsPad` hands the gamepad to the game while the stage is open (L1 and R1 do not change the frequency), `trustNote` adds a game specific warning to the trust note, and with `renderResults` the game draws the result section itself. When more than one game is registered, the Game button first opens a local Choose a Game screen. The general texts do not depend on the game and call the person who sets up the table the host, and a game can give some of them in its own words (dealer, hand and deck in Renk) with `game.<game>.<key>` keys. For a turn based game the transport and the table manager do not change, and a real time game also uses the game link of the voice engine.

The layout is a star: the dealer is the single authority, and players talk only to the dealer. The voice engine has no shared message order between peers, order is kept only per peer, so a single device decides the order of the game. The full state of the deck exists only on the dealer's device. The dealer checks every move with the rule engine and sends a full state to each seat separately: the public view (the seats and their card counts, the top card, the active color, the direction, the draw pile and discard counts, the latest events), the recipient's own hand and the result of the recipient's last move travel in one message, and no diffs are sent. A lost message is therefore repaired by the next one. The player's device checks the incoming state strictly (the field sets, the seat order, its own hand size, a card total of 108) and drops an invalid one silently. The rules are checked on the dealer's device. That is why the Wild +4 restriction is enforced automatically and there is no challenge step. The Last Card rule applies in both rule sets. When a round ends the remaining hands are not revealed, and the results show only card counts and points. Each round is scored on its own, and no total is kept across rounds. After a finished round the dealer returns to the lobby with New Round, and the seated players keep their seats.

The message types and their formats are fixed. The invite (`invite`), the player's decline (`decline`), the dealer's rejection (`reject`) and the close (`close`) are plain JSON, carry only numeric ids and codes and never touch the game state. Every message that changes or reads the game state (`join`, `act`, `sync`, `leave` and `state`) travels in the inner envelope. The format and field set of every type are exact, and a message with the wrong format or with extra or missing fields is dropped, so there is no downgrade. A message that is not in the role table is dropped too, for example a `state` sent to the dealer.

The inner envelope is the `2.` format of direct messages (`E2EE.dm`): it is sealed with the shared key computed with `box.before` from the identity keys of the two people and carried inside the group key envelope of the voice signal. When opening, only the other person's current verified public key is tried, and old keys are not. The plaintext is separated from direct message and private call plaintexts by the `ctx: 'game'` field and bound by the type (`k`), the table id (`g`, 16 hex digits), the room (`ch`), the sender (`from`) and the recipient (`to`). Because the shared key is the same in both directions, an envelope reflected back to the dealer does open, but it is rejected because its `from` field does not match. So even someone who knows the group key and runs the server cannot read a player's hand, cannot forge a move in their name and cannot move a table's message to another table, room or person. The trust in the inner envelope is the same as for direct messages: a key is pinned on first sight, and a man in the middle attack on first contact is caught only by comparing safety numbers. A person for whom the inner layer cannot be set up (their own identity is locked, or the other side's key could not be verified or has changed) is not let into the game, and the reason is shown on both sides. A join from someone whose profile has not loaded yet is held for up to 10 seconds and handled once the profile arrives. The dealer sends no invite to a person they blocked and does not answer that person's messages, and a player does not show an invite from a dealer they blocked. Blocking after the invite has arrived has the same result: the stored invite is deleted, the badge on the Game button and the entry in the Notifications list go away, and the person can set up a table again. The "Blocked" chip appears only on the dealer's screen.

Versions and counters prevent old messages from being replayed. Every invite carries a random value specific to the recipient (`ni`). `join` sends this value back, the dealer accepts each value once, and every `state` reflects the recipient's accepted value. A player does not accept a state whose value does not match, so an old state cannot be forced on a reloaded page. The player's counted messages (`act`, `sync`, `leave`) carry a counter that increases per person (`seq`): a lower counter is dropped, and the same counter only brings back the result. While a move is pending no `sync` is sent, and only the same move is repeated with the same counter. A move carries the round number (`rd`) and the step count of the rule engine (`step`), and a move from an earlier round or a past turn is rejected. The table version (`r`) increases with every state change. A player does not accept an older version, and accepts the same version only if it carries a newer counter result.

The dealer keeps at most one message in flight per seat. Changes that arrive in the meantime only mark the seat as pending, and the next send carries the newest state. The reply to a rejected move goes at most once per second per seat, the reply to `sync` at most once every 5 seconds, and `reject` and the `close` for an unknown table at most once every 5 seconds per person. If the dealer has sent nothing to a seat for 15 seconds, it sends the last state again, and in the lobby it repeats the invite with the same value every 15 seconds to an invitee who has not answered. A player resends an unanswered move every 10 seconds with the same counter, asks with `sync` after 25 seconds without a valid state, and after 45 seconds ends the table with the reason "the dealer cannot be reached" and sends `leave` to the dealer. A seat whose turn has lasted more than 60 seconds gets an "Away" chip. The dealer can remove any seat with Remove from Seat (while the game is on, from the Seats list below the table), and there is no automatic removal. If the person has reloaded the page and has not pressed Return to Game yet, the farewell also goes with the value of the pending invite, so the reloaded page sees that it was removed too. On a new connection with the same peer id the dealer first sends that person an invite with a new value, then the state. A player who reloads the page and returns to the voice room sees a "Return to Game" offer, and accepting it brings them back to their seat and their counter where they left off. If the dealer reloads the page the table is lost: the dealer answers a message for a table it does not have with `close`, and the players see that the game is over. The stored invites of members who are not seated are kept alive as well. A live dealer repeats the invite on every new connection, so if the connection the invite came from becomes ready again and no new invite arrives within 10 seconds, the stored invite is deleted. For a stored invite that has not been renewed for 60 seconds, a probe (`sync`) goes to the dealer. A dealer without the table answers with `close`, and a dealer with the table ignores the probe of someone without a seat. This also repairs a lost `close`. The invite that seats me (Return to Game) is repeated every 15 seconds by a live dealer, so it is not probed and is deleted if it has not been renewed for 60 seconds. An ICE restart on the same connection does not affect the game.

The deck is shuffled on the dealer's device with `nacl.randomBytes` using the Fisher-Yates (Durstenfeld) method, and numbers are picked without bias by rejection sampling. The canonical order of the deck is fixed. The deck is shuffled for a new round, when the first card is a Wild +4, when the draw pile runs out and when a player leaves. The dealer's own Last Card and Catch presses do not cross the network, so they are processed with a 300 ms delay and race the players' presses that arrive at the same time more fairly. The dealer's turn moves have no delay.

The aim is a single table per room at a time. Someone who has seen an invite cannot open a new table, and the Game button becomes Invite (Game in Progress if a game is on). A dealer in the lobby gives way only while nobody but the dealer is seated at the table: to a table in play with at least two seats, or to a lobby with more seats or with a smaller table id. Both sides compute the same result from the same data. The losing dealer closes their table and shows the incoming invite. A lobby with seated players never closes by itself, so a plain invite that someone in the room makes up in their own name cannot throw the seated players off the table. Stored invites are kept by the dealer's id, so someone else's invite with the same table id cannot shadow the real dealer's invite. Because of blocking and racing openings, two tables can run in the same room, and since each table is isolated by its own id this is not a technical problem. An incoming invite does not open the stage: the Game button becomes "Invite", an entry with a View Table button appears in the Notifications list, and at most one notification arrives from the same dealer every 30 seconds. In the first version the game plays no new notification sound.

### Hexball and the game data channel

The Hexball rule engine is in `43-hexball-kural.js` (`window.TelsizHexball`), the physics in `44-hexball-fizik.js` (`window.TelsizHexballPhysics`), the networking in `45-hexball-ag.js` (`window.TelsizHexballNet`) and the interface in `46-hexball.js`. The rule engine and the physics are pure, and the network layer gets its clock, timers and sending from outside, so the tests run it with a fake clock and a fake network that produces delay, jitter and loss. The rule engine carries only the low rate work: teams, starting a match, goals, time, golden goal and the result. These travel through the table manager in the inner envelope, as in Renk. Assigning teams, starting a match, goal, time up and stopping are host only moves, and the rule engine rejects them from anyone else with `not_host`. Goal and time up moves carry the match number (`mt`), and a move that arrives late from an earlier match is rejected with `stale`. The view has no hidden information, and a player's own view is empty.

After Start the table moves to the Teams screen. The rule engine deals the seats to the Red and Blue teams in turn. A team has at most 4 people, and the rest are Spectators. Everyone can pick their own team, and the host can move people to a team or to the spectators. Start Match becomes active when each team has at least one person and the game link with everyone on a team is ready. When a match starts, the host's device creates a new match id (`epoch`, 16 hex digits) and gives the people on the teams slots, which are the player numbers on the data channel. The presets (Classic by default):

| Preset | Field (units) | Goal mouth | Time | Goal limit |
| --- | --- | --- | --- | --- |
| Quick (`quick`) | 720x360 | 120 | 3 minutes | 3 |
| Classic (`classic`) | 880x440 | 140 | 5 minutes | 5 |
| Long (`long`) | 1040x520 | 160 | 10 minutes | none |

The team that reaches the goal limit wins, and when time runs out the team ahead wins. If the score is level when time runs out, a golden goal is played and the first goal ends the match. In the preset without a goal limit the match ends at the 255th goal, because the score is a single byte in the snapshot. The match clock runs only while the ball is in play, and stops during the kickoff and in the 2 seconds after a goal. Red kicks off odd numbered matches and Blue even numbered ones, and after a goal the team that conceded kicks off. During the kickoff everyone stays in their own half until the ball is touched, and the defending team waits outside the center circle. The host can end the match without a winner with Stop Match. If a team runs out of people during a match, the match ends without a winner, and if fewer than two people remain at the table, the table ends. When a match ends, the result and the last 10 goals show on the same screen. The host starts a new match with the same teams with Play Again, or ends the table with Back to Lobby and goes straight back to the lobby. Since the table takes no new people after Start, newcomers join this way, and the seated people keep their seats.

Real time data needs dozens of messages per second, so it does not go through the table manager or the server. `voice.js` can open a single data channel per peer on top of the voice connection (the game link): its label is `telsiz-game`, and it is unordered and without retransmission (`ordered: false`, `maxRetransmits: 0`), so a lost snapshot is not sent again and does not hold up the next one. The channel travels encrypted on the same connection as the audio, with SCTP inside DTLS, and a TURN relay cannot read its content. The voice engine does not know what the data means, it only sets up and limits the channel: at most 512 bytes per message and at most 240 incoming messages per second per peer, and anything beyond that and data that is not binary are dropped. When the send buffer of the channel goes over 16384 bytes, sending is skipped and stale data is not queued. A channel opened by the other side is accepted only if its label and settings match, there is no other channel with that peer and it is not a private call, and a channel that does not match is closed right away. If both sides open one at the same time, the channel of the smaller peer id stays. The functions are `openGameLink`, `closeGameLink`, `gameLinkState` and `sendGameData`. The voice engine reports three more events to the game layer: the channel opened (`link-open`), an open channel closed (`link-close`) and the channel could not be opened (`link-failed`). Incoming data goes through `onGameData` to `36-oyun.js` without passing through the table manager, and from there to the interface of the game at the table (`onData`).

The channel is not added to the first offer but opened when needed: while the table is in play, the host opens a channel with everyone at the table (spectators included), and the data section (`m=application`) is added to the connection through the renegotiation path that screen sharing and the camera use. The check that counts the audio and video m lines does not count the data section, so a failed negotiation that adds the data section is not counted as a screen or camera error. If the data section cannot be added to the negotiation with a peer (the offer exceeds the envelope limit of the server, one side cannot apply the offer or the answer, or the other side rejects the data section), the game link with that peer is not opened again in this voice session (`openGameLink` returns `blocked`), so the connection is not rebuilt over and over. This record is cleared when the voice session ends or the person leaves the room. If the connection is rebuilt, the new connection has no channel and the host opens it again. When the offer that adds the data section for the first time is rolled back in a collision (by the polite side, for example when the other side turns on its camera at the same moment), Chromium never puts the data section into the later offers of that connection again, not even after a new channel is created, and the channel never opens (tried in Chromium 141). That is why the polite side does not roll such an offer back in a collision, and instead rebuilds the connection with that peer once per voice session with the channel already in the first offer. The other side cannot make an offer before the first offer is answered, so this collision cannot happen on the new connection. If the browser leaves the data section out of an offer altogether, the offer is not sent, so no offer and answer loop forms. If the same thing happens a second time, the game link with that peer is blocked.

The messages of the network layer are binary and little endian. The first byte is the version (1) and the second byte is the type:

| Message | Direction | Fields | Bytes |
| --- | --- | --- | --- |
| HELLO | host to player | match id (8 bytes, zero in the lobby), slot (255 for a spectator), step and snapshot rate | 13 |
| HELLO_ACK | player to host | the match id and slot of the HELLO it received | 11 |
| INPUT | player to host | sequence number (u16), the step of the newest snapshot it received (u32), buttons (bit 0 kick), two axes (i8, -127 to 127) | 11 |
| SNAP | host to player | step (u32), phase, time left (tenths of a second), two scores, the recipient's last processed input, the ball, and for each player the slot, position, velocity and flags (bit 0 kick held) | 22 + 10 x player count, at most 102 |

Positions are fixed point in 1/8 unit and velocities in 1/64 unit per step. A message whose length, version, type or any field does not match is dropped.

A channel that looks open does not mean a game is listening on the other side: in an older client the browser opens the channel too. That is why the host sends HELLO when the channel opens and repeats it every 250 ms until HELLO_ACK arrives. If no acknowledgment arrives within 5 seconds after the channel opens, the channel does not open within 15 seconds after it starts opening, or it cannot start opening at all for 15 seconds (the voice connection is not ready, or the person has no voice connection), the link fails and the host sees the person as "No Connection" (an older client or a blocked link). A failed link whose channel never opened is tried again once the voice connection is ready again. A peer whose link failed but whose channel stays open gets a HELLO every second, and a late acknowledgment is accepted. Start Match stays inactive until the link of everyone on a team is ready, and the host can move the person to the spectators or remove them from the seat. A player who gets no handshake from the host within 15 seconds, whose channel cannot be opened or whose voice engine does not know the game link sees the same state. At the start and end of every match the handshake is repeated with the new match id: a peer that does not acknowledge the new id gets no snapshots and its input is not processed.

The host is authoritative, and only the host runs the physics. The physics reads no clock and counts steps: a step is 1/60 of a second and is solved in two substeps, and the same world always gives the same result for the same inputs. The host runs the loop with a `setTimeout` chain and a counter that accumulates the elapsed time instead of `requestAnimationFrame`, and sends players 30 snapshots per second. When sending to a peer is skipped, that peer gets 20 snapshots per second for 2 seconds, and when the voice engine's estimate of the upload speed (`uplinkEstimate`) stays below 40 kbps per ready link, everyone does. If two loop runs are more than 250 ms apart (browsers may throttle the timers of a background tab), the match pauses and everyone sees "The host's tab is in the background, the match is paused." The match goes on once the loop runs regularly for 500 ms. The desktop app turns off background timer throttling (`disable-background-timer-throttling`), so this pause is not expected there. Because the host's own input does not cross the network, it is held back for the measured average round trip time of the players, at most 80 ms, and not held back while there is no measurement. This is the counterpart of the 300 ms delay on the dealer's presses in Renk. The host sends the goal and time up events of the physics to the rule engine as moves, and the physics and the rule engine reach the same score and result. When someone leaves or is removed from their seat during a match, their disc leaves the field and the match goes on with the same id: if they touched the ball last, the next goal is credited to the team, and the kickoff formation counts only the remaining players. When a match ends, the host sends one last snapshot with the final score to the peers that acknowledged. The result state of the table arrives later on the signaling path than data on the data channel, so in the meantime the player sees the last frame and no connection warning.

The host processes input only from the peer of the person seated at the table, and only for a person with a slot in the match. At most 120 inputs per second per peer are processed, an old sequence number is dropped and the axes are clamped. Spectators receive snapshots, and their input is not processed. A player accepts HELLO and SNAP messages only from the host's peer and drops a snapshot older than the newest step. A player draws by interpolating with a buffer of two snapshots (about 66 ms at 30 Hz), and the buffer grows up to 150 ms with jitter. There is no client prediction, and a player draws their own disc from the snapshots too. If the newest snapshot is older than 400 ms, "Slow Connection" appears on the screen. During a match, while the stage is open and the person has a slot in the match, the L1 and R1 buttons of the gamepad do not change the frequency (`36-oyun.js` `gameOwnsPad`, `21-band.js` `padPoll`). When the stage is minimized the match goes on and keys and controls are released. The details of the interface are in [DESIGN.md](DESIGN.md#game-table).

The host could cheat: a modified client could move the discs at will, make up goals or ignore inputs, and the player's device cannot verify the physics. This is written at the end of the trust note on the Set Up a Table, lobby and invite screens. Any peer in the room can open a channel. The one channel rule, the size and rate limits, the host processing input only from the peers of seated people and the player listening only to the host's peer limit the effect of this. The trust in the game link is the same as for audio, see [Limits](#limits).

### Rate budget

Game messages share the rate limit of voice signals: 120 requests per user per 10 seconds (`signalLimit`, `signalWindowMs`). A request that hits the limit does not count against the budget. Below, N is the number of seats at the table (at most 8) and M the number of people in the voice room.

| Event | Sent by the dealer | Sent by a player |
| --- | --- | --- |
| Opening the table | M - 1 invites | none |
| Joining | N - 1 states | 1 `join` |
| Starting | N - 1 states and M - N invites to those not seated | none |
| Move (the dealer's included) | N - 1 states | 1 `act` |
| Rejected move | 1 state, at most 1 per second per seat | 1 `act` |
| Idle refresh | 1 per seat every 15 seconds, about 4.7 per 10 seconds with 8 seats | after 25 seconds of silence, 1 `sync` at most every 10 seconds |
| Unanswered invite in the lobby | 1 per invitee every 15 seconds | none |
| Reconnection | 1 invite and 1 state per peer | 1 `sync` or the pending move |
| Stored invite probe | without the table, at most 1 `close` per person every 5 seconds | at most 1 `sync` per stored invite every 60 seconds |

In a typical game (8 seats, a move every 3 seconds) the dealer sends about 23 requests per 10 seconds, and about 70 with one move per second. The single flight rule leaves at most one pending request per seat. The voice engine retries after 1, 2 and 4 seconds on a 429, a network error or a 5xx answer, and if the message still cannot be delivered, the dealer backs off for 2, 4, 8, 16 and 30 seconds for that seat and intermediate states are skipped. Because every state carries the last 8 events, the events of the skipped states are still announced. The worst moment is when all of the dealer's connections are rebuilt at once: for 7 connections about 7 offers, 70 ICE candidates, 7 invites and 7 states, about 91 requests in total. This is below the limit but close. The voice engine does not expose the count in the shared window, so the game layer cannot know this in advance.

The real time data of Hexball does not count against this budget. Only team, match start, goal, time and result moves go through the table manager, so the number of requests in a match depends on the number of goals: every goal means N - 1 states from the host. When the game link is opened, the host sends a renegotiation offer to each seat and the player replies with an answer. Since the channel is opened again when connections are rebuilt, at the worst moment above a Hexball table sends one more offer per seat.

### Deliberately left out

- Games in private calls.
- Verifiable shuffling: there is no way to show that the dealer shuffled the deck honestly. The canonical deck order and the deal order are fixed in preparation for it.
- Handing over the dealer role: the game ends when the dealer leaves.
- A challenge step for Wild +4, "Skip Turn" and automatic removal of an idle player from their seat.
- A total score across rounds and revealing the remaining hands at the end of a round.
- Watching from outside the voice room: a person who is not in the voice room cannot receive signals. Entering a voice room asks for microphone permission, so joining without a microphone is not possible either. The Spectators of Hexball are people seated at the table.
- A new notification sound, a floating invite notification, a system notification and camera video in the seats.
- An owner setting that turns games off, or a separate game permission. These would need server changes.
- Client prediction, joining in the middle of a match, more than 4 players per team and sound effects in Hexball.
- Verifiable physics: players cannot check that the host runs the physics honestly.
- Binding the DTLS fingerprints to messages in the inner envelope. This would also protect the connections in a voice room against someone who knows the group key and runs the server (see [Limits](#limits)), and it was left as separate work that covers audio as well.
- Other games (Pişti, Dört Taş and XOX). All of them will be added on top of the table manager through the same app contract.

## Desktop app

The desktop app (`desktop/`) is built with Electron for Windows and Linux. In the web version the interface code comes from the server on every visit. In the desktop app the files in the `public/` folder are copied into the app at build time, the sha256 value of each one is written to an integrity manifest, and the app verifies every file at startup. The page loads from the privileged `telsiz://app/` scheme and no interface file is downloaded from the server.

The page's API requests are forwarded to the configured server by a proxy in the main process. Only the required headers pass, redirects are not followed, and no cookies or cache are used. The server address must be `https://`, with the only exception being a server on the same computer. Windows run with context isolation and the sandbox on. Permissions are limited to the microphone, the camera, notifications, writing to the clipboard and full screen for the Full screen button of the broadcast stage, and are granted only to the main frame of the app window, so subframes cannot go full screen. Screen capture is granted only through the app's own picker. Background windows can only show notifications, every other permission including the microphone and the camera is denied. New windows are not opened. The only exception is the floating window: the app window can open it only at `about:blank` with a single-use name it gets from the main process, after the window opens the main process checks again that the opener is the main frame of the app window, the window has no preload script and all permissions and navigations are denied. The only allowed subframe is the YouTube player of Telsiz DJ: a direct child frame of the app window's main frame, and only for the `https://www.youtube-nocookie.com` origin. Frames inside it and all other subframes are blocked. In the packaged app, Electron fuses turn off the Node.js mode and the `NODE_OPTIONS` variable. The detailed security architecture is in [desktop/README.en.md](../desktop/README.en.md).

Updates (`desktop/src/lib/updates.js`): the Windows installer and the Linux AppImage use electron-updater to read `latest.yml` or `latest-linux.yml` from the GitHub release, download the new version in the background and verify it with its sha512. It is installed only when the user chooses Restart and update. The portable exe and the .deb only read the latest stable release from the GitHub API and show a notice that opens the release page. The Check for updates automatically setting is on by default, and while it is off no request is sent to GitHub. The page cannot pass any address or file path over IPC, and the release page is opened only with the project's GitHub release addresses.

## Limits

Telsiz is designed to hide content from the server, but it does not hide everything, and like any software it cannot be guaranteed to be free of vulnerabilities. The project has not had an independent security audit. The known limits are as follows.

**Metadata the server sees.** The server cannot see message, file, profile or DJ content, but it does see: which user is online when and their status (including the invisible status), if automatic idle is on when a person's sessions went inactive (members see it too once all of their sessions are idle), usernames, room names and the room list, roles, who writes to which room and direct message conversation, when and with what size, edit and delete events, the sizes of uploaded files, friendship and block relations, typing status (who is typing in which conversation and when), who is in which voice room, their mute and deafen state and whose camera is on, who calls whom in direct messages and when, whether a call is voice or video and how long it lasts, the timing and size of voice signals (game messages included), which voice rooms have a Telsiz DJ state, the size of the DJ envelope and who updates it and when, if the owner has turned on search by song name who searched for which song name with `/play` (plain text, not logged), for reports who reported whom, which message (including whether it is a direct message), for what reason and when, and who resolved the report and when, session labels derived from the browser's user agent (for example the browser and operating system name), and the IP addresses of connecting devices. Because the cover photo is downloaded only when a profile card is opened, the server can also see who opens whose card and when. Display names, about me, custom status text, profile pictures, cover photos and report notes (including a message text attached to a report) are encrypted. The frequency name, the frequency introduction and the frequency photo are not encrypted and are public.

**Code delivery in the web version.** In the web version the app code comes from the server on every visit. An active attacker who takes over the server, or an intermediary that terminates the HTTPS connection (a reverse proxy or a tunnel provider), could serve modified code and steal keys. This is the known limit of every end-to-end encrypted app that runs in a browser. The desktop app removes this risk because it carries the interface inside itself.

**The group key.** The group key is shared by everyone on the server. Anyone who knows the key can read all group content as long as they can reach the encrypted data. There is no forward secrecy. Someone removed from the group still knows the old key, and a new key protects only the content that follows. Anyone who sees the invite link learns the key.

**Direct messages.** Direct messages have no forward secrecy either, and the same identity keys are used for a long time. A member who has the group key and also runs the server, or colludes with it, could publish a fake identity binding. On the first conversation the key is not pinned yet, so such a man in the middle attack goes unnoticed. A later change is caught by the key change warning thanks to pinning on first sight, while an attack on the first conversation is caught only by comparing safety numbers. Verify the safety number over another channel for important conversations. When a password is reset by the owner or the command line, old direct messages can no longer be read, after a reset with the recovery code they stay readable.

**Recovery code.** The code is equivalent to the password: whoever gets it can change the password and read the direct messages. The code is shown only once, a downloaded file and clipboard history (including a cloud clipboard) can leave it exposed. If the response of the recovery request is lost on the network, the new code is lost too, the person signs in with the new password and creates a new code in Settings. The server can block recovery by deleting or altering the code data, but it cannot find the 128 bit secret by guessing offline and cannot hand out a fake wrapped key without the client noticing.

**A malicious server and integrity.** The server cannot open envelopes, but it can serve the envelopes it stores however it likes. The plaintext of a message carries the author and the room id, but no message id or version. A malicious server can therefore replay or duplicate an old message, hide messages, and roll back an edit by showing the earlier version of a message. Text rooms have no sender signatures, and content is authenticated only with the shared group key. Anyone who has the group key, for example a member colluding with the server, can create messages in another member's name.

**Key renewal and removing members.** The client accepts content sealed with any key in its keyring, not only the active key. A member removed from the group still knows the old key, so with the server's help they can add new content sealed with the old key, and they can read history protected by the old key. Kicking someone from the frequency deletes their account, but it cannot take back the group key the person knows, and the person can register again until the invite code is renewed. Creating a new group key does not renew the invite code. When a member is kicked from the frequency or banned, create a new group key to protect the messages that follow, renew the invite code and share the new invite link only with the remaining members.

**Keys stored on the device.** Group keys, the personal identity key and the session token are in the browser's local storage. Anyone with access to the device or the browser profile can access them too.

**Voice, screen sharing, camera and game data.** Because audio and video flow directly between people, participants can see each other's IP address. In a voice room the trust in these connections rests on the group key: the DTLS fingerprints that authenticate a connection travel in signals encrypted with the group key. Someone who knows the group key and runs the server, or colludes with it, could replace the fingerprints in the signals with their own and get in the middle between two people, reading and changing audio, video and the game data channel. A server that does not know the group key cannot do this. The signals of a direct message call are encrypted with personal keys, so there this is possible only while the other person's key is not pinned yet. In a full mesh each person sends their audio, shared screen and camera video to every recipient separately. The upload speed of someone with their camera on is split into one camera stream for every other person in the room, so as people and cameras increase, members' connections may not keep up and video quality drops. The design is therefore meant for small groups: a voice room is limited to 8 people by default and 12 at most, and the number of cameras on at the same time to 4 by default. The server enforces the camera limit but cannot see the video content. The capacity recommendation in the settings is an estimate, not a measurement. The default STUN server belongs to Google, and devices that join a voice room contact it. If TURN is configured, its username and password are static and are sent to every signed in person who joins a voice room.

**Search.** Search runs only on the device, over history fetched page by page from the server and decrypted. At most 20000 messages per room are scanned, messages whose key is not on the device cannot be searched, and scanning takes time for large histories.

**YouTube.** When consent is given for a YouTube track, the player loads from Google's servers. Google sees the IP address of that device and which video is played, may collect tracking data and may show ads. The device of a person who does not give consent does not connect to YouTube. No request goes to Google for file tracks. When the server owner turns off the YouTube source, this is enforced on the members' devices. Since the DJ state is encrypted, the server cannot enforce it on the content, and a modified client could still add a YouTube track to the queue. If search by song name is on, the search text reaches the server as plain text and goes to YouTube from the server's IP address, so YouTube sees the server's address, not the address of the person searching. Since this search does not use the official API, it goes against YouTube's Terms of Service (the ban on automated access), which is why it is off by default and the owner turns it on after confirming. If YouTube changes its response format or blocks the server's address, the search turns itself off for one hour after repeated failures, and adding by link keeps working.

**Telsiz DJ media controls.** The name of the playing track and the name of the voice room are given to the system's media controls and the lock screen (Media Session). The name comes from the end-to-end encrypted DJ state and so leaves the app, and it is also visible on a locked screen. It can be turned off in Settings > Privacy > Media controls. Play and Pause there only affect the player on that device.

**Telsiz DJ author information.** The "added by" information in the queue is checked against the author records reported by the server. A malicious server could show this information wrongly, but it cannot change the contents of the tracks.

**Games, the dealer and the host.** The dealer shuffles the deck on their own device, and that device technically knows every hand. The interface does not show other hands on the dealer's screen, but a modified client could show them, arrange the deck at will and break the rules. The player's device only checks that the incoming state is consistent (field formats, its own hand size, the card total) and cannot verify that the shuffle was honest. This is written in the lobby right above the Join button and as a chip at the table. A player's hand goes only to them, encrypted with the identity keys of the two people. The trust in the inner envelope is the same as for direct messages: a key is pinned on first sight, and a fake identity binding on first contact is caught only by comparing safety numbers. Someone who knows the group key and runs the server cannot read hands or forge moves, but can drop messages and forge the plain messages (invite, decline, reject and close). The effect is a denial of service: they can close a table or prevent joining. A member of the room can also make up a plain invite in their own name. This only closes a lobby where nobody but the dealer is seated, and the stored invites of a blocked person are ignored. Last Card and Catch presses are judged in the order they reach the dealer, so network delay affects the outcome. The dealer's own presses are processed with a 300 ms delay, which reduces the dealer's advantage but does not remove it. Someone who reloads the page and does not return to the voice room stays in the roster as a "ghost", which is an existing behavior of the voice engine. A ghost player holds up the game when their turn comes, and the dealer removes them with Remove from Seat in the Seats list below the table. If the dealer stays a ghost, the players see that the game is over after 45 seconds. If the same person joins the voice room from another device, they lose their seat. The server cannot tell game messages apart from other voice signals and sees only their timing and size. In Hexball the host's device runs the physics and players cannot verify it: a modified client could move the discs at will, make up goals or ignore a player's input. This is written in the trust note. The real time data of Hexball is protected only by DTLS, not by the inner envelope, and there is no hidden information in the game data. Someone who gets in the middle as described above could watch the match and spoil the game by changing inputs or snapshots. Teams, goals and the result travel in the inner envelope of the table manager, so they cannot forge those messages, but they could affect the course of the match by changing the inputs that reach the host. In a real time game network delay gives the host an advantage, and holding back the host's input by at most 80 ms reduces it but does not remove it. In the browser the match pauses if the host's tab goes to the background and its timers are throttled. The Telsiz server sees neither the content nor the traffic of the game data channel, only the timing and size of the renegotiation signals that add the channel. If a TURN relay is used, it sees only the amount and timing of the encrypted traffic.

**Availability.** The server can withhold or delay messages, delete accounts and stop the service. End-to-end encryption protects the confidentiality of content, it does not guarantee that the server keeps running.

**Resource use.** The upload quota is shared by the whole server, and there is no per user storage quota. Even with rate limits, a signed in member can use up the shared quota and server resources. Share the server only with people you trust.

**Shared files.** Files of any type can be shared. Since the server cannot see the contents of files, no malware scanning is possible.

**Unsigned binaries.** The single file server and the desktop app are not code signed. Windows SmartScreen may show a warning on first start. Files can be verified with `SHA256SUMS.txt` on the release page. The Node.js base image of the Docker image is selected by a version tag and is not pinned by digest. The npm package is published through npm trusted publishing (OIDC), without a long lived token and with provenance. The Node.js binary used for the linux-arm64 build is verified against `SHASUMS256.txt` from nodejs.org, and no GPG signature is checked. Desktop updates are unsigned too: electron-updater verifies the package against the sha512 in the release's `latest.yml`, but that file is in the same GitHub release. The integrity of updates therefore rests on the security of the GitHub account and repository, and the repository owner and everyone with write access should use two factor authentication (2FA). Update checks show GitHub the IP address and the app version and can be turned off in the settings. The portable exe and the .deb are not updated by themselves. No single file server or desktop package is published for macOS.

**Use on a home network without https.** On an `http://` connection the content is still end-to-end encrypted, but session information travels unencrypted on the network, and an active attacker on the same network could modify the app code.
